# 德州扑克 Web 游戏 · 项目规划书

> 版本：v2.0  ·  日期：2026-08-18
> 状态：技术选型与任务规划已定稿，待启动实施
> 变更（v2.0）：联机模式改为纯真人联机（去掉 AI 补位）；视觉风格改为像素风（参考小丑牌 Balatro）

---

## 一、项目概述

构建一款基于 Web 的德州扑克游戏，面向浏览器即开即玩。核心追求：
精美的牌桌界面、沉浸的"德式"刺激性体验、忠于正统玩法的同时引入趣味道具、
以及房间制真人同桌与一键登录账户体系。

本规划书对四个核心需求进行技术拆解，给出技术选型与理由、系统架构、核心模块设计，
并输出分阶段可执行的任务规划。

|---|---------|---------|-------------|

## 三、技术选型

### 3.1 联机模式：纯真人联机

**选择：真人实时同桌，凑齐最低人数开局，无 AI 补位。**

理由：
- 德州的乐趣核心在于"与人博弈"，真人对手才有真实的诈唬、试探与心理战，
  这是刺激性的根本来源（需求2）。
- AI 决策再聪明也缺乏"人对人"的紧张感，会稀释德州的魅力。
- 房间设置最低开局人数（默认 2 人即可开局，最多 6~9 人），
  玩家进入房间后坐下，凑齐即可开始；未满员时显示"等待其他玩家加入"。

技术影响：后端 WebSocket 房间状态机需处理"等待 → 满足开局条件 → 开始"的调度；
无需 AI 决策模块，降低后端复杂度，但需做好"长时间未开局"的等待体验
（座位状态可视化、玩家就绪提示、可随时离开）。

### 3.2 视觉风格：像素风（参考小丑牌 Balatro）

**选择：复古像素美术 + 高饱和霓虹配色 + CRT 滤镜 + 强 juice 动效。**

参考 Balatro 的视觉语言，关键特征：
- **像素美术**：像素风卡牌、筹码、UI 元素；`image-rendering: pixelated` 保持锐利像素。
- **高饱和霓虹配色**：深紫/深蓝黑背景，配红/黄/绿/蓝/紫的霓虹强调色，强反差制造紧张感。
- **强 juice 动效**：屏幕震动（screen shake）、粒子爆发、卡牌弹跳放大、数字跳动放大、
  闪光与全屏高光——这是小丑牌"刺激性"的灵魂，直接服务需求2。
- **CRT 复古质感**：扫描线 overlay + 轻微暗角 + 像素字体，营造老式游戏机的沉浸氛围。
- **像素字体**：标题用 Silkscreen / Press Start 2P，数字用 VT323，强化复古游戏感。

理由：
- 小丑牌已验证"像素风 + 强 juice"能把扑克的刺激性做到极致，与德州的需求高度契合。
- 像素风美术资产可程序化生成（CSS/SVG 绘制像素卡牌与花色），无需重度美术依赖。
- 高饱和霓虹 + 震屏粒子的视觉冲击力，远超拟真牌桌的"精致但平淡"。

### 3.3 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 前端框架 | React 18 + TypeScript | 生态成熟，组件化适合复杂牌桌 UI；TS 保证状态/事件类型安全 |
| 构建工具 | Vite | 极速 HMR，开发体验好 |
| 样式 | Tailwind CSS + 自定义像素 CSS | Tailwind 做布局/配色，自定义 CSS 处理像素渲染、CRT 滤镜、像素字体 |
| 动效 | Framer Motion + tsParticles + 自写 Canvas | Framer Motion 做卡牌/筹码变换；tsParticles/Canvas 做粒子爆发与闪光；自写震屏 hook |
| 像素字体 | Silkscreen / Press Start 2P / VT323（Google Fonts） | 复古游戏机字体，强化像素风气质 |
| 状态管理 | Zustand | 轻量，适合实时游戏状态（socket 同步） |
| 实时通信 | Socket.io (client) | 房间状态实时同步 |
| 后端 | Node.js + TypeScript + Express + Socket.io | 与前端同语言，类型可共享，实时能力成熟 |
| 数据存储 | 内存 + JSON 文件持久化 | 无需安全，账户/道具/战绩轻量持久化即可，零运维 |
| 卡牌美术 | CSS + SVG 程序化绘制像素卡牌 | 无需图片资产，动效可控，锐利像素 |
| 测试 | Vitest | 前后端通用，重点覆盖规则引擎 |
| 代码组织 | 单仓多包 (frontend / backend / shared) | 共享类型与规则，避免重复 |

## 四、系统架构

```
浏览器 (React SPA)
   │  REST（登录/账户/大厅列表）   +   WebSocket（房间内实时）
   ▼
Node 服务 (Express + Socket.io)
   ├── 账户模块        一键注册/登录，token，筹码/道具背包
   ├── 房间大厅        创建/加入/离开，座位管理，开局调度
   ├── 游戏引擎        德州规则状态机 + 底池/边池
   ├── 道具系统        道具校验、效果应用、冷却/次数
   └── 持久化          JSON 文件（账户、背包、战绩）
```

通信划分：
- REST：无状态操作——注册/登录、大厅房间列表、个人资料/战绩。
- WebSocket：有状态操作——进入房间、座位、下注动作、道具使用、实时局面广播。

实时广播模型：服务端为唯一真相源（authoritative server），客户端只发送动作，
服务端推进状态机后向房间内全员广播统一局面（含可观测信息过滤：不泄露他人底牌）。

## 五、核心模块设计

### 5.1 德州规则引擎（shared + backend）

- 牌型：Card { suit, rank }；Deck 洗牌。
- 牌力评估：7 选 5 最优组合，支持高牌 → 皇家同花顺全部 9 档，含 kickers 比较。
- 状态机阶段：waiting → ready → preflop → flop → turn → river → showdown → 结算 → 回合循环。
- 下注动作：fold / check / call / raise / all-in；大小盲注；最小加注规则。
- 底池：主底池 + 边池（all-in 情况），按贡献分配。
- 信息过滤：广播局面时对非本人底牌做遮蔽（满足道具"偷窥"的前提）。

### 5.2 房间与账户系统（backend）

- 账户：{ id, username, token, chips, inventory, stats }。
- 一键注册：前端一键生成用户名 → 服务端建账户 → 返回 token，浏览器 localStorage 持久化；
  下次进入自动凭 token 免登录。无需密码、无需邮箱（按需求"不需要安全"）。
- 房间：{ id, name, seats[], gameState, config }；支持创建/加入/离开/坐下/站起。
- 座位：6 人桌（可配置 9 人），空座显示"等待加入"；纯真人，无 AI 占位。
- 开局调度：坐下人数 ≥ 最低开局人数（默认 2）时，任意玩家点"准备"即可发起开局；
  全员准备或房主确认后开始。未满员时持续显示等待状态。

### 5.3 视觉与动效系统（Balatro 式 juice，需求1/2 核心）

- 像素卡牌：CSS/SVG 绘制，花色与点数用像素符号，翻牌用 3D flip + 发光描边。
- CRT 滤镜：全屏 scanline overlay + 暗角 vignette + 轻微色差，营造复古质感。
- 震屏（screen shake）：All-in、大额加注、胜负揭晓时触发，强度随事件分级。
- 粒子爆发：tsParticles 实现，翻牌/加注/胜利时迸发霓虹粒子。
- 卡牌弹跳放大：关键牌（如公共牌揭示、showdown 胜牌）放大 + 弹性回弹。
- 数字跳动：底池、筹码变化时数字滚动放大再回落，强化"筹码博弈"的爽感。
- 回合计时器：环形倒计时 + 超时将至时变红闪烁，制造紧迫感。
- 音效：8-bit 风格音效（发牌、筹码、翻牌、加注、胜利、道具），配合像素风。

### 5.4 趣味道具系统（需求3 的差异化核心）

道具定位：不修改德州基础规则，作为"每局可用次数受限"的增益/变数层，增加趣味与博弈维度。

| 道具 | 效果 | 使用时机 | 获取 |
|------|------|---------|------|
| 透视镜 | 翻牌前偷看一张即将翻开的公共牌 | 翻牌前 | 每日签到/对局奖励 |
| 偷窥眼 | 偷看指定对手的一张底牌 | 翻牌前/后 | 对局奖励 |
| 换牌术 | 丢弃并替换自己的一张底牌 | 翻牌前 | 对局奖励 |
| 重洗牌 | 重新发当前阶段的公共牌 | flop/turn/river | 稀有掉落 |
| 保险券 | 本局若输牌，返还 50% 已投入筹码 | 任意 | 每日签到 |
| 双倍赏金 | 本局赢牌额外获得 100% 底池奖金 | 任意 | 稀有掉落 |

设计要点：
- 每局每人可用道具次数上限（默认 1 次），防止破坏平衡。
- 道具效果由服务端权威应用与校验，客户端仅发起请求与播放动画。
- 道具使用伴随专属像素动效与 8-bit 音效（透视闪光、偷窥扫描线、换牌翻转、重洗粒子），
  强化"刺激性"与"趣味性"。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 实时状态机复杂、边池错误 | 玩法正确性 | 阶段 1 单测覆盖；边池专门用例 |
| 强 juice 动效性能不足 | 流畅性（需求1） | 优先 transform/opacity；粒子数量上限；必要时降级 |
| 纯真人房间长时间凑不齐人 | 等待体验差 | 低门槛开局（2 人即可）；等待状态可视化；随时可离开 |
| 道具破坏平衡 | 趣味变破坏性 | 每局次数上限 + 服务端权威校验 |
| 像素美术一致性 | 视觉精致度 | 程序化生成统一像素组件；建立像素对齐规范 |
| 单服内存状态丢失 | 账户/战绩 | 关键数据 JSON 持久化；房间局状态可丢失 |
